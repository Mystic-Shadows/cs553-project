# lessons learned

When building out a non-trivial API, design and planning is paramount. Being able to identify what the database will contain, both in content and structure, and how the user will interact with it is important. Furthermore, authentication and authorization can almost be seen as another consumer since their data must be stored, users must be verified, and the code for authentication and authorization can get messy and fragile when not done properly. Draw diagrams of how the user will interact with the system and how the services will interact with each other.

This was an area I messed up. The original design up to milestone 4 did not include allowances for authorization in particular. This led to many unique implementations of authorization logic that are harder to find and debug. It is also a nightmare to maintain and change. From the beginning, I should have asked more questions about where I was going instead of just implementing the milestones one at a time without considering the future milestones. Planning out an implementation from the architectural level instead of bashing together code without diagrams is what I’d do differently were I to do it again.

There are two design decisions that I want to highlight. The first is the middleware module which contains a bunch of validators. These made it easy to add that logic into every relevant route that needed it and could contain special validation for specific routes. This kept my codebase tidy (at least before milestone 5). The other decision was the Authorizations table. This is what allowed me to make members for the projects. In hindsight, I should have also expanded this table to include the owners too (instead of storing them with the projects) in order to keep all the fine-grain authorization in one place. This table, while having to make another set of routes, made a 1-to-many relationship trivial.

A security risk to watch out for, if another student were to do this project, is to make sure all the routes are protected properly. Plan to make authorization easy ahead of time instead of having to handjam it for every route. Otherwise, make sure you log everything. My program, past the login/registration routes, logs the user as well. This would allow someone to do an audit of the system if necessary.

A technical concept I learned was another proper use for lambdas. I always enjoy a good design pattern, but I have seen some absolutely atrocious lambda code in my, albeit short, professional career. Primarily I have used them to satisfy a library function call or when a task almost explicitly called for the Strategy pattern, but otherwise avoid them. To see them returned by a function for the middleware is interesting. It seemed like a clean way to do it without overcomplicating the codebase. 

Another technical concept I learned was all the networking components. From Cors to Express to Authorization - even Java/Type-script - I have never done this kind of development. The closest I’ve done was probably in an undergrad CPE networking class which deals at a much lower level for the labs (if it isn’t obvious by this point, I am a backend dev by trade). The closest thing I’ve done was with Dash 1.x in Python with a sqlite database (and was only ever hosted on localhost).

My final advice is to both plan and not be worried about needing to do large refactors (give yourself the time to do them). This would’ve helped me especially towards the end.
